## Why

molejo renamed the token a document uses to declare its spec version. The
`molejo` field was the integer `1` or `2`; it is now the `MAJOR.MINOR`
string of the release that introduced it — `"0.1"`, `"0.2"` — and the
integer form is refused rather than aliased, so a stale document fails
loudly instead of being guessed at.

solid-node never writes that field. `MolejoNode._shape_spec()` returns
`rendered.to_dict()` and the document travels through the widget
opaquely, exactly as ADR-057 intended. But three pieces of committed test
data and one type declaration wrote the integer down by hand, and those
hand-written copies are now wrong. Ten widget tests fail against the
current molejo:

```
SpecError: spec.molejo: must be a spec version string, one of '0.1', '0.2', got 1
```

The framework's own behaviour is not in question — this is a dependency's
vocabulary changing under test data that should never have restated it.

## What Changes

- `solid_node/viewers/widget/src/flexible.test.ts` and
  `src/document.test.ts`: the `SPRING_SPEC` constants declare
  `molejo: '0.1'` instead of `molejo: 1`. `flexible.test.ts` feeds that
  constant to the real evaluator, which is why eight of its cases fail;
  `document.test.ts` only checks document shape, so its copy is stale
  without yet being red.
- `solid_node/viewers/widget/src/parity-fixture.json`: regenerated by
  `tools/generate_parity_fixture.py` rather than hand-edited. The
  generator takes the spec from `flexible_fixture.Spring().render()`, so
  the correct version arrives from molejo itself and the fixture stays a
  producer-generated artifact.
- `solid_node/viewers/widget/src/molejo.d.ts`: `SPEC_VERSION` is declared
  `string`, not `number`. solid-node never reads it, but an ambient
  declaration that contradicts the module it describes is a latent
  `tsc --noEmit` failure.
- `docs/adrs/NODE/ADR-057-the-flexible-leaf-and-spec-carried-geometry.md`:
  the illustrative document at its "third node shape" section shows
  `"molejo": "0.1"`, so the ADR does not teach a form the evaluator
  rejects. The decision it records is untouched.

And the hole the rename exposed:

- `solid_node/viewers/widget/src/flexible.ts`: a `flexible` node whose
  spec the bundled evaluator cannot read is refused **at construction**,
  naming the node and the evaluator's own reason, exactly as an unknown
  `tech` already is. Today that case escapes as a raw molejo `SpecError`
  thrown from `evaluate()` inside the render loop — unnamed, and on a
  frame rather than at load.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `viewer-package`: one ADDED requirement — a flexible node whose spec
  the bundled evaluator cannot read is refused by name at construction,
  rather than throwing from the render loop.

Nothing else moves. `flexible-parts` and `viewer-package` describe the
molejo document *opaquely* on purpose: the adapter's embedded form is
"the shape's own serialization", and the viewer hands the spec to the
bundled evaluator without reading it. Neither names a molejo spec
version, and neither should — the version is molejo's vocabulary, and the
opaque treatment is exactly why this rename's blast radius is test data
rather than source. `viewer-package`'s `version: 2` / `version: 3` is the
solid-node *document* version, a different thing that is unaffected.

The added requirement is not a consequence of the rename; the rename is
what made an existing gap observable. The viewer already refuses an
unknown `tech` by name rather than rendering a wrong shape, and the same
posture was simply never extended to a spec the evaluator cannot read.

## Impact

- `solid_node/viewers/widget/src/flexible.test.ts` — `SPRING_SPEC`.
- `solid_node/viewers/widget/src/document.test.ts` — `SPRING_SPEC`.
- `solid_node/viewers/widget/src/parity-fixture.json` — regenerated.
- `solid_node/viewers/widget/src/molejo.d.ts` — one declared type.
- `solid_node/viewers/widget/src/flexible.ts` — the `FlexibleShape`
  constructor gains the spec check beside the `tech` check.
- `docs/adrs/NODE/ADR-057-…md` — one illustration.
- Dependency: the widget already declares `molejo` as an optional peer at
  `^0.2.0` (`package.json`), so nothing there moves. The Python side
  declares no molejo dependency at all on this branch; `docs/leaf-nodes.rst`
  documents the editable install instead.
- Upstream: molejo `0.2.0`, which carries spec version `"0.2"` and reads
  `"0.1"` unchanged. The originating evidence is that repository's
  `number-the-spec-with-the-package` change.

## Out of scope

- **The stale local widget bundle.**
  `solid_node/viewers/widget/dist/solid-widget.js` inlines a molejo-0.1-era
  validator, but `dist/` is gitignored and this workspace symlinks it from
  the primary checkout; the project's own convention is never to build
  inside a worktree. It is a local artifact that a rebuild from the primary
  checkout refreshes, not repository content this cycle can commit.
- **The `release-0-6-0-packaging` branch.** Its `pyproject.toml` pins
  `molejo[brep]==0.1.*` and its widget `package.json` pins `^0.1.0`. That
  is another branch's in-flight release work, and the pin cannot honestly
  move to `0.2.*` until molejo `0.2.0` is published. It is named here so
  the dependency is not lost, and left to that branch.
- **Archived OpenSpec records.** The archived
  `2026-08-29-flexible-leaf-node/design.md` shows the old form in a
  historical design sketch. An archive records what was decided when it was
  decided; editing it would falsify the record for a cosmetic gain.
- **Teaching solid-node to read the molejo version.** It has no reason to,
  and the added refusal does not: it asks the evaluator whether it can read
  the spec and reports the evaluator's own answer, never parsing a version
  itself. Opacity is the decision ADR-057 made, and this change is evidence
  for it, not against it.
- **Recovering from an unreadable spec.** Refusing by name is the whole
  behaviour. Rendering the rest of the document without the node, or
  substituting a placeholder shape, would be the "wrong or missing shape"
  the existing `tech` refusal exists to prevent.
